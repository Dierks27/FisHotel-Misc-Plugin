Added Shop App section — "FisHotel Shop", an installable web app for the wet room, so the tank work no longer goes through a WordPress login. Not an app from a store: on Android the browser's *Install app* (on an iPhone *Add to Home Screen*) gives it its own icon and a full-screen window, and it updates with the site. Off until switched on; needs HTTPS and says so otherwise. The app lives at `home_url( '/?fh_shop_app=1' )` (a query on the home address, so it works with any permalink setting) with a web app manifest (`FisHotel Shop`, standalone, dark, 192 / 512 px icons and a maskable one), an *Install app* button when the browser offers one, and install steps for Android and iPhone on the admin page. **Devices**: a PIN works only on an enrolled device — enrolled by a shop manager or administrator logged in to WordPress on it (*Set up this device*), or by a one-time link with a QR code (drawn by the Clean Room's encoder) that is good for ten minutes and one use; opening the link shows one button and the tap enrols, so a link preview cannot spend it and nobody types a WordPress password on the shop tablet. A 256-bit token goes into a `Secure`, `HttpOnly`, `SameSite=Lax` cookie for a year, renewed on use; the server keeps only its SHA-256. FisHotel Tools → Shop App → Devices lists them (name, enrolled by, last used, who is unlocked, locked out or not) with *Revoke* — which takes effect on the device's next request — and *Clear lockout*. A device that is not enrolled never sees a keypad. **People and PINs**: a name and a PIN of 4–6 digits (one length for the shop, a setting, so the keypad sends the PIN with its last digit), stored as a hash made with a per-person salt and a site secret, unique among active people — a clash says only "Choose a different PIN.", and a typed PIN is compared with everybody before the answer is given; switching a person off destroys their PIN, and a new PIN, another account or switching off ends the session that person has open on every device (a session started with a PIN somebody else learned does not live on); on the form the PIN shows as it is typed, since it is typed once. Each person's work is recorded under their own WordPress account or under one shared `fishotel-shop-staff` account the section creates (no e-mail address, a role with no capability, it cannot log in). **Unlocking**: twelve very large keys, no on-screen keyboard, every press lights its key, a wrong PIN shakes and clears; a correct PIN starts a shop session — a signed cookie checked against the device row on every use — lasting two hours from the last use (Settings: 30 minutes to 12 hours, counted from the last use or from the unlock); the screen shows who is unlocked and has *Lock*, which ends the session on the server. Five wrong PINs within fifteen minutes lock the device for five minutes, doubling each time up to a day, logged and shown on the Devices list; a correct PIN gives back only its own try and never clears the wrong ones before it (so a PIN of one's own is no way to walk through everybody else's), every wrong PIN is in the log — the device and which try, never the digits — and a device whose tries are used up without a lockout on record gets it on the next try instead of refusing every PIN for good. **A shop session is not a WordPress login**: it is recognised only on the Clean Room's Front Desk page and its four AJAX actions — classified by method, path and parameter names before any cookie is believed — as the person's account holding exactly the Front Desk's capability, and only while that handler runs (an administrator's own account, and a multisite super admin, are clamped the same way); an AJAX call is nobody's until its action starts — whatever acts for "the current user" on `init`, `wp_loaded` or `admin_init` on a field added to the POST (a basket's add-to-cart) sees a visitor, WordPress fires the visitor's hook and the gate hands over to the real action there; on wp-admin, every other admin-ajax action, admin-post, the REST API, the shop front, My Account and checkout the device is not logged in. WooCommerce's basket cookies and the account's saved basket are kept out of those requests and page caches are told `DONOTCACHEPAGE`. Nothing in the Clean Room section is changed; other sections add shop-floor screens with `fishotel_shop_app_allowed_requests`. **The app's home**: who is unlocked and *Lock*, buildings then tanks (the Front Desk's own data), and *Scan a tank label* where the browser can read codes from the camera (`BarcodeDetector`; only the tank number is taken from a scan); a tank opens the Front Desk's own tank screen with a bar added (back to the tanks, who is unlocked, *Lock*). **The laminated labels** (`/?fh_front_desk=1&tank=N`) keep working: with a WordPress login and on any device that is not enrolled exactly as before (the page is byte-for-byte the same), on an enrolled device with a live session the tank opens without a WordPress login, with nobody unlocked the keypad comes first and then that tank. **No connection**: a save that gets no answer opens *MAY NOT BE SAVED* (the server may have written it all the same) — what was entered is still there, *Retry* — and goes through by itself when the connection returns; every save carries a save id — the same on every retry and when that very entry is saved again after *Back to the entry* — so one that did reach the server is answered from memory instead of written twice, for a week (the sheet may be found open after a weekend), and an id names one entry: with other content it is written, not answered "saved"; a session that ran out under an open page brings the keypad up, says whose PIN saves the waiting entry, and saves it after that PIN — when somebody with another account unlocks instead, the screen says *NOT SAVED — enter it again* before the tank is loaded afresh. The tank picker is redrawn from every fresh state, so a tile never shows what an older one said. The service worker is registered for the app's own address only and keeps nothing but the static shell, the manifest and the icons, fetched without cookies — never the state, a tank or a name. **Access log** (append-only, on the admin page and mirrored to the Health log): devices enrolled and revoked, links made, unlocks, wrong PINs, locks, lockouts and their clearing, people added or changed — never a PIN. Four tables (`fh_shopapp_devices`, `_people`, `_log`, `_saves`) by dbDelta behind the autoloaded `fishotel_shopapp_db_version` (written only once the tables and the newest column exist), all `$wpdb` in one store file, names cut to their columns by characters, not bytes; an ordinary front-end request costs the section no query. No e-mail is sent, no order, stock or money is touched. Headless PHP and node tests for the PINs, the lockout, the devices, the sessions, the gate, the labels, the saves, the store, the admin page, the app's addresses, the app script and the service worker.
